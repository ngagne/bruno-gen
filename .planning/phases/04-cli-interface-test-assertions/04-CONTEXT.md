# Phase 4: CLI Interface & Test Assertions - Context

**Gathered:** 2026-04-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Build the Commander.js CLI entry point (`src/cli.ts`) that orchestrates the existing `parse()` → IR → `generate()` pipeline, implements all CLI flags (`--format`, `--tests`, `--dry-run`, `--config`), handles exit codes, and generates inline Bruno `post-response` test assertion scripts when `--tests` is provided.

**Inputs:** Spec file path (YAML/JSON/.graphql), output directory, CLI options
**Outputs:** Bruno collection directory structure on disk (or stdout for `--dry-run`), proper exit codes, summary output

**Requirements covered:** CLI-01 through CLI-10, TEST-01 through TEST-04 (14 total)

**Not in scope:** Config file discovery/merging (Phase 5), plugin hooks (Phase 5), library API surface (Phase 5). The CLI calls the existing internal `generate()` directly — config and plugin integration wire into that same function later.

</domain>

<decisions>
## Implementation Decisions

### CLI Architecture
- **D-01: Hybrid CLI** — Default mode is thin: parse spec → call `generate()` → print summary. `--verbose` mode breaks into step-by-step orchestration (detect format, load spec, parse, validate, generate files, summary) with progress reporting
- **D-02: Commander.js** — CLI framework. Already specified in ROADMAP; supports subcommands for future phases (`brunogen validate`, `brunogen init`)
- **D-03: Entry point** — `src/cli.ts` added to `tsup.config.ts` entry array to produce `dist/cli.js` (matching existing `package.json` `"bin"` declaration for `gen-bruno`)

### Test Assertion Generation
- **D-04: Inline Bruno `post-response` blocks only** — Tests embedded in `.bru` files, run inside Bruno's test runner. No separate CI test files for v1
- **D-05: Tier 2 assertion depth** — Status code assertion + required fields presence checks (one assertion per required field from response schema). When spec provides a response example, add one bonus assertion checking an example value
- **D-06: Test scripts only with `--tests` flag** — No test code generated by default (TEST-04). When `--tests` is set, every request `.bru` file gets a `post-response` block

### CLI Flags
- **D-07:** `--format <tag|path|flat>` — controls folder grouping strategy (tag = default, path = URL path segments, flat = no folders)
- **D-08:** `--tests` — enables post-response test assertion generation
- **D-09:** `--dry-run` — prints structure tree to stdout without writing files. `--dry-run --verbose` prints full `.bru` file contents
- **D-10:** `--config <path>` — accepted now, wired through to generator options. Full config file discovery/merging deferred to Phase 5
- **D-11:** Positional args: `<spec>` (file or directory path), `[output]` (output directory, defaults to `./bruno-output`)

### Output Formatting
- **D-12: TTY-aware output** — `process.stdout.isTTY` detection. TTY mode: `chalk` for colors, `ora` for spinner during generation, `cli-table3` for summary. Non-TTY/CI mode: plain text, no spinners, no ANSI colors
- **D-13: Summary content** — file count (requests, folders, collection.bru, env files), warning count, generation time
- **D-14: Error formatting** — clean messages by default (file path + human-readable description). Stack traces only with `--verbose`

### Exit Codes
- **D-15: Exit 0 on success** — including when warnings are present (CLI-07)
- **D-16: Exit 1 on unrecoverable error** — invalid spec, missing output dir, parse failure (CLI-08)
- **D-17: Warnings without halting** — unsupported features or spec issues logged as warnings, generation continues (CLI-09)

### Test Assertion Integration
- **D-18: Test generation wired through request generator** — When `--tests` is active, `request-generator.ts` appends a `post-response` block to each `.bru` file. The test generator is a new module (`src/generators/test-generator.ts`) consumed by the request generator
- **D-19: Test assertions use Bruno's native `expect` and `res` APIs** — `res.getStatus()`, `res.getBody()`, `expect(value).to.equal(expected, message)`, `expect(obj).to.have.property(name)`

### the agent's Discretion
- Exact spinner message text and timing
- `cli-table3` table column names and layout details
- Internal module organization within `src/cli/` (commands, options, formatting submodules)
- Error message copywriting
- Dry-run tree formatting details (indentation, icons)

</decisions>

<specifics>
## Specific Ideas

### Test assertion patterns (Tier 2)
```bru
post-response {
  // Status code assertion
  const status = res.getStatus();
  expect(status).to.equal(200, "expected status 200");

  // Required fields presence
  const body = res.getBody();
  expect(body).to.have.property("id", "required field 'id' missing");
  expect(body).to.have.property("name", "required field 'name' missing");

  // Bonus: example value assertion (when spec provides example)
  expect(body.status).to.equal("available", "expected example value 'available'");
}
```

### Dry-run structure tree
```
my-api/
├── collection.bru
├── environments/
│   └── default.bru
├── Users/
│   ├── folder.bru
│   ├── GET-users.bru
│   └── POST-users.bru
└── Pets/
    ├── folder.bru
    └── GET-pets.bru
```

### CLI command surface
```
brunogen <spec> [output]

Options:
  --format <tag|path|flat>   Folder grouping strategy (default: tag)
  --tests                    Generate post-response test assertions
  --dry-run                  Print structure tree without writing files
  --config <path>            Custom config file path
  --verbose                  Detailed output with progress and stack traces
  -h, --help                 Show help
  -V, --version              Show version
```

### Exit code behavior
- Invalid spec file → exit 1, error message with file path
- Missing output directory (can't create) → exit 1, error message
- Unsupported features in spec → exit 0, warning logged, generation continues
- Successful generation → exit 0, summary printed

### TTY detection behavior
- `process.stdout.isTTY === true` → colors, spinner, table
- `process.stdout.isTTY === false` or `NO_COLOR` env var set → plain text
- `CI` env var set → always plain text (overrides TTY)

</specifics>
