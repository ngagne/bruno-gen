# Roadmap: Bruno Collection Generator

## Overview

Build a Node.js 24 CLI tool and importable library (CommonJS + ESM) that converts OpenAPI 3.x, Swagger 2.0, and GraphQL schemas into Bruno API collections. Six phases take us from an empty repo to a published npm package: project scaffold with IR types, parser layer, Bruno generator layer, CLI interface, library API with config/plugins, and publishing.

## Phases

- [x] **Phase 1: Project Scaffold & IR Types** — Foundation: TypeScript, tooling, build pipeline, and the Intermediate Representation type system
- [ ] **Phase 2: Parser Layer** — OpenAPI 3.x, Swagger 2.0, and GraphQL parsers that produce the unified IR
- [ ] **Phase 3: Bruno Generator Layer** — IR to .bru file generation: requests, collection, folders, environment, auth
- [ ] **Phase 4: CLI Interface & Test Assertions** — Commander.js CLI with all flags, optional test assertion generation
- [ ] **Phase 5: Library API, Config & Plugins** — Programmatic API (CJS+ESM), config file system, plugin hooks
- [x] **Phase 6: Publishing & Polish** — npm publish, README, docs, final validation

## Phase Details

### Phase 1: Project Scaffold & IR Types
**Goal**: Fully configured project with TypeScript, linting, testing, build pipeline, and the complete IR type system that all parsers and generators share.
**Depends on**: Nothing (first phase)
**Requirements**: [QUAL-01, QUAL-02, QUAL-03, QUAL-04, QUAL-05]
**Success Criteria** (what must be TRUE):
  1. `npm run build` produces dual CJS and ESM output via tsup with no errors
  2. `npm test` runs Jest suite with 80%+ coverage threshold enforced
  3. `npm run lint` passes eslint; `npm run format` runs prettier; .editorconfig active
  4. TypeScript strict mode compiles with zero errors across all source files
  5. IR type system includes all required interfaces (CollectionIR, EndpointIR, ParameterIR, SchemaIR, SecurityScheme variants, ResponseIR, etc.)

Plans:
- [ ] 01-01: Initialize project — package.json, tsconfig.json (strict, Node 24), tsup config for dual CJS/ESM
- [ ] 01-02: Configure tooling — eslint config, prettier config, .editorconfig, Jest config with coverage thresholds
- [ ] 01-03: Define IR type system — all TypeScript interfaces for the unified intermediate representation
- [ ] 01-04: Set up CI pipeline — GitHub Actions workflow (lint, test, build) with coverage reporting

### Phase 2: Parser Layer
**Goal**: Three parsers (OpenAPI 3.x, Swagger 2.0, GraphQL) that each produce the unified IR from their respective input formats.
**Depends on**: Phase 1 (IR types must exist)
**Requirements**: [PARSE-01, PARSE-02, PARSE-03, PARSE-04, PARSE-05, PARSE-06, PARSE-07, PARSE-08, PARSE-09, PARSE-10]
**Success Criteria** (what must be TRUE):
  1. Tool parses a valid OpenAPI 3.1 YAML spec and produces correct IR with all endpoints, params, bodies, and auth schemes
  2. Tool parses a Swagger 2.0 JSON spec and produces equivalent IR (normalized to OpenAPI 3.x structure)
  3. Tool parses a single `.graphql` SDL file and produces IR with queries and mutations as POST endpoints
  4. Tool parses a directory of `.graphql` files and merges them into a single IR
  5. Tool resolves `$ref` references including circular references without stack overflow
  6. Tool reports validation errors with file/line context for invalid specs
  7. All 10 parser requirements pass with golden file tests against known specs (Petstore, Stripe subset)

Plans:
- [ ] 02-01: OpenAPI 3.x parser — uses @apidevtools/swagger-parser to parse YAML/JSON, produce IR, handle $ref resolution
- [ ] 02-02: Swagger 2.0 parser — normalize to OpenAPI 3.x structure (basePath, schemes, definitions → components)
- [ ] 02-03: GraphQL SDL parser — parse .graphql files, extract queries/mutations, map to IR endpoints with POST body
- [ ] 02-04: GraphQL directory parser — discover and merge multiple .graphql files into single IR
- [ ] 02-05: $ref resolution and circular reference handling — depth limits, safe dereferencing
- [ ] 02-06: Spec validation layer — validate specs, report errors with context, graceful degradation

### Phase 3: Bruno Generator Layer
**Goal**: Convert the unified IR into Bruno .bru files — collection structure, requests, folders, environment variables, and authentication.
**Depends on**: Phase 2 (parsers must produce IR to generate from)
**Requirements**: [REQ-01, REQ-02, REQ-03, REQ-04, REQ-05, REQ-06, REQ-07, REQ-08, REQ-09, REQ-10, AUTH-01, AUTH-02, AUTH-03, AUTH-04, AUTH-05, ENV-01, ENV-02, ENV-03, ENV-04]
**Success Criteria** (what must be TRUE):
  1. Generated collection opens in Bruno and displays all requests with correct methods, URLs, and headers
  2. Request bodies populated with example values from spec schemas (not empty or placeholder-only)
  3. Example responses from spec visible as Bruno response examples in the UI
  4. Environment file contains {{baseUrl}} and all auth variables; requests reference them correctly
  5. Requests grouped by tag (OpenAPI) or query/mutation type (GraphQL) in Bruno folder structure
  6. All auth scheme types (apiKey, HTTP bearer, HTTP basic, OAuth2/OIDC) generate correct env vars and request headers
  7. OperationIds with special characters, spaces, and reserved words sanitized to valid filesystem paths

Plans:
- [ ] 03-01: Output layer — file system ops, directory structure creation, path sanitization, atomic writes
- [ ] 03-02: Collection generator — collection.bru with name, version, default auth
- [ ] 03-03: Request generator — method, URL with {{baseUrl}}, path params, query params, headers, body
- [ ] 03-04: Response examples generator — convert spec response examples to Bruno response format
- [ ] 03-05: Folder generator — tag-based and path-based grouping, folder.bru metadata
- [ ] 03-06: Environment generator — {{baseUrl}}, auth variables, environments/ directory structure
- [ ] 03-07: Auth handler — apiKey, HTTP bearer/basic, OAuth2/OIDC env var generation and request header injection

### Phase 4: CLI Interface & Test Assertions
**Goal**: Full Commander.js CLI with all flags (format, tests, dry-run, config) and optional test assertion generation for requests.
**Depends on**: Phase 3 (generators must work to wire CLI to them)
**Requirements**: [TEST-01, TEST-02, TEST-03, TEST-04, CLI-01, CLI-02, CLI-03, CLI-04, CLI-05, CLI-06, CLI-07, CLI-08, CLI-09, CLI-10]
**Success Criteria** (what must be TRUE):
  1. `brunogen ./openapi.yaml ./output` generates a complete Bruno collection with exit code 0
  2. `brunogen ./schema.graphql ./output --tests` generates collection with post-response test scripts
  3. `brunogen ./openapi.yaml ./output --dry-run` prints generated output to stdout without writing files
  4. `brunogen ./invalid.yaml ./output` exits with code 1 and reports validation errors
  5. `brunogen ./openapi.yaml ./output --format path` groups requests by URL path instead of tag
  6. Non-TTY output is clean (no spinners, no ANSI colors) for CI/CD compatibility
  7. Warnings for unsupported features displayed without halting generation (exit 0)

Plans:
- [x] 04-PLAN: Phase 4 plan created (6 waves: CLI entry, output formatting, exit codes, format flag, test generator, test wiring)

### Phase 5: Library API, Config & Plugins
**Goal**: Programmatic API (CJS+ESM), config file discovery and merging, and plugin system with transformIR and preOutput hooks.
**Depends on**: Phase 4 (CLI must work; library API exposes same functionality programmatically)
**Requirements**: [LIB-01, LIB-02, LIB-03, LIB-04, LIB-05, LIB-06, CFG-01, CFG-02, CFG-03, CFG-04, CFG-05, CFG-06]
**Success Criteria** (what must be TRUE):
  1. `import { generate } from 'bruno-gen'` works in ESM project
  2. `const { generate } = require('bruno-gen')` works in CommonJS project
  3. TypeScript project importing the library gets full type hints from included .d.ts files
  4. `CollectionBuilder.fromSpec(spec).withOptions(opts).generate(dir)` produces same output as `generate()` function
  5. Config file `brunogen.config.yml` in CWD is discovered and merged with CLI flag overrides
  6. Plugin with `transformIR` hook can modify the IR before generation (tested with a simple header-injection plugin)
  7. Plugin with `preOutput` hook can modify .bru content before it's written (tested with a comment-injection plugin)

Plans:
- [ ] 05-01: Library API — generate() function, CollectionBuilder fluent class, options type
- [ ] 05-02: Dual CJS/ESM exports — package.json exports field, tsup config verification, import tests
- [ ] 05-03: TypeScript declarations — .d.ts generation, types field in package.json
- [ ] 05-04: Config system — file discovery, YAML/JSON parsing, merge strategy (defaults < config < CLI)
- [ ] 05-05: Plugin system — plugin interface definition, transformIR and preOutput hook execution
- [ ] 05-06: Plugin config support — plugins array in config file, plugin resolution and loading

### Phase 6: Publishing & Polish
**Goal**: Package ready for npm — README with full docs, examples, validation against real-world specs, and npm publish.
**Depends on**: Phase 5 (all functionality complete)
**Requirements**: [PUB-01, PUB-02, PUB-03, PUB-04]
**Success Criteria** (what must be TRUE):
  1. Package installs cleanly via `npm install bruno-gen` and CLI is available on PATH
  2. ESM import and CommonJS require both work from a fresh npm install
  3. README includes: installation, CLI usage with examples, library API docs, config file docs, plugin docs
  4. Tool successfully generates valid Bruno collections from real-world specs (Stripe, GitHub, or Petstore OpenAPI)

Plans:
- [x] 06-01: README.md — installation, CLI reference, library API reference, config docs, plugin docs, examples
- [x] 06-02: Real-world validation — test against stripe-like, github-like, petstore fixtures
